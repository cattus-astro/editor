## 글자 합성

safari에서는 contenteditable 의 위치를 실제 캔버스가 그려야하는 곳 시작점에 위치시키고, compositionupdate 이벤트 발생한 글자로 계속 해당 부분의 글자를 캔버스에 그리고 compositionend 이벤트 발생전까지는 계속 update 에서 넘어오는글자로 대체해서 그린다. compositionend 이벤트가 발생하면 해당 글자를 최종적으로 캔버스에 다시 덮어쓰고 contenteditable 의 innerText 를 초기화하고 contenteditable 시작 위치를 한칸 다음으로 옮긴다.

chrome 에서는 contenteditable 의 위치를 실제 글자가 그려지는곳 다음으로 위치시키고(실제 우리가 편집툴에서 기대하는 커서의 위치), keyup이나 keydown 으로 매 글자 입력 받을 때마다 오토마타를 이용해 합성글자를 만든다. 실제 글자가 합성이 완료되면 이를 캔버스에 최종적으로 그리고 다음 입력칸으로 커서를 이동시킨다.
합성이 완료될때까지 캔버스에 글자를 덮어쓰는 행위는 safari와 동일하다.

이렇게 safari 와 chrome에 동작이 엇갈리는 이유는 키보드, 운영체제, 브라우저마다 다른 IME(Input Method Editor) 를 사용하다보니 글자가 합성되는 이벤트의 순서가 다르기 때문이다.
chrome 에서는 직접 오토마타를 구현하는 방식을 채택했는데, 이는 모두 원하는 이벤트 순서로 묶을 수 있기 때문이다.
safari 에서도 chrome 과 같이 직접 구현한 오토마타를 적용하면 됐겠지만 그러지 않은 이유는 safari 만의 합성어를 만드는 규칙때문인것으로 추측된다.
자세하게 알 순 없지만 예전 safari 에서 글자가 합성되는 과정에서 keydown 이벤트에서 잘못된 key(229)가 수신되는 경우가 있었던 걸로 보인다 (https://bugs.webkit.org/buglist.cgi?quicksearch=keydown%20composition%20229)

즉, keydown 또는 keyup 이벤트로부터 글자를 수신해 직접 합성어를 만드는 과정을 수행하기에 safari 의 이벤트의 신뢰성이 낮으니 safari 자체 IME 에서 합성해주는 걸 그대로 사용한것으로 보인다.

chrome 방식은 한글만이 아니라 일본어, 중국어 등 모든 CJK IME를 직접 구현해야 하며 브라우저/OS/키보드 조합마다 keydown 동작이 다를 수 있고, 구버전 호환성도 불확실하기때문에 safari 에서 사용한 방식을 사용할 예정이다.

💡 실전 구현을 위한 3가지 디테일
캔버스 덮어쓰기할 때의 clearRect (잔상 방지)
update 이벤트가 올 때마다 캔버스에 'ㄱ', '가', '강'을 그릴 텐데요. 덮어쓰기 전에 반드시 직전에 그렸던 임시 글자의 영역만큼 ctx.clearRect()로 캔버스를 지워주셔야 합니다. 안 지우고 그 위에 겹쳐서 그리면 픽셀의 안티앨리어싱(Anti-aliasing)이 겹치면서 글자가 점점 굵고 지저분해지는 렌더링 잔상 버그가 생깁니다.

'한 칸 다음'의 기준은 픽셀(Pixel) 너비
contenteditable의 위치를 '한 칸 다음'으로 옮길 때, 단순히 우측으로 일정 간격 이동하는 것이 아니라, 방금 확정된 글자('강')를 CanvasRenderingContext2D.measureText('강').width로 계산하여 정확한 픽셀 너비만큼 left 좌표에 더해주어야 합니다. 폰트마다, 심지어 같은 한글이라도 글자마다 미세하게 픽셀 너비가 다를 수 있기 때문입니다.

compositionend 이후의 빠른 일반 타자 방어
사용자가 '강'을 치고 스페이스바(띄어쓰기)나 영어를 엄청나게 빠르게 연달아 치면, compositionend와 input 이벤트가 거의 동시에 들어옵니다.
따라서 contenteditable의 innerText를 초기화('')할 때, 방금 들어온 일반 키보드 이벤트 데이터까지 날아가지 않도록 이벤트 핸들러의 실행 순서(Angular의 Zone.js 또는 RxJS 파이프라인)를 잘 제어해서 모델 상태와 DOM 상태의 싱크를 맞춰주시면 됩니다.
